# App Releases (APK upload) — Plan

> Add a release to an already-registered app by uploading a new APK (+ a
> version name / changelog / optional metadata updates). "Publishing a release"
> becomes: place the APK where `fdroid update` expects it, write the release's
> data into fdroid-native files, run `fdroid update`, and read the result back
> from the files fdroid produced.
>
> **Architectural pivot:** the manager stops keeping its own authoritative copy
> of apps and releases (the `AppInfo` / `AppRelease` tables). fdroid's own files
> are the source of truth:
>
> - app-level "what is this app" → `metadata/<packageName>.yml`
> - "what versions exist" + per-version facts → `repo/index-v1.json` / `repo/index.xml`
>   (both regenerated by `fdroid update`) and the APKs themselves (`repo/*.apk`)
>
> The SQLite DB shrinks to the things fdroid does **not** hold: repo config and
> app signing-key material.

---

## 1. Goal

1. `POST /api/apps/{packageName}/releases` — operator uploads an APK (multipart
   `apk`) plus an optional `changelog`; the version (code/name) comes from the
   APK's own manifest. The manager signs it if needed, drops it into the fdroid repo (fdroid renames it
   to its canonical name), writes the changelog/metadata files, and runs
   `fdroid update`.
2. `GET /api/apps` and `GET /api/apps/{packageName}` read from fdroid's index
   (`repo/index-v1.json`), **not** from the DB.
3. `GET /api/apps/{packageName}/releases` reads the version list from the same
   index (name, code, size, hash, signer, SDK levels, permissions) + the
   per-version changelog sidecar.
4. `DELETE /api/apps/{packageName}/releases/{versionCode}` removes the APK +
   its changelog file and re-indexes.
5. Remove the `AppInfo` / `AppRelease` tables as the authoritative store
   (migration below). `AppKey` and `RepoConfig` stay; `AppKey` is re-keyed by
   `packageName` instead of a numeric app id.

## 2. Research — what fdroid's own files contain (verified)

Verified against fdroidserver **2.4.5** (installed locally) and the actual
generated files already present in this repo (`data/repo/*`).

### 2.1 `repo/index-v1.json` — the machine-readable index (source of truth)

Real sample (this repo, `data/repo/index-v1.json`, prettified):

```json
{
  "repo":  { "name": "My F-Droid Repository", "url": "...", "timestamp": 1787756622, "version": 20002 },
  "apps": {
    "org.example.helloworld": {
      "name": "Hello World",
      "summary": "A simple hello world test app",
      "description": "Test application for F-Droid repository",
      "license": "MIT",
      "categories": ["repo"],
      "added": "2026-08-26",
      "lastupdated": "2026-08-26",
      "web": "", "source": "", "tracker": "",
      "versions": {
        "1": {
          "versionCode": 2,
          "versionName": "1.0.0",
          "file": { "hash": {"sha256": "9b13bbd6…"}, "name": "/org.example.helloworld_2.apk", "size": 16865 },
          "manifest": {
            "usesSdk": { "minSdkVersion": 21, "targetSdkVersion": 34 },
            "signer": { "sha256": ["2045fac3…"] },
            "usesPermission": []
          }
        }
      }
    }
  },
  "packages": { "1": { "AppId": 2, "VersionCode": 2 } }
}
```

Facts that drive the design:

- **App id is the package name** (the `apps` dict key), matching the
  `metadata/*.yml` file stem (see `plans/done/app-metadata.md` §2.1).
- **Everything the current `AppInfo`/`AppRelease` tables store is derivable**
  from this one file: name, summary, description, license, web/source/tracker
  (AppInfo); and per-version versionCode, versionName, sha256, size, signer,
  min/target SDK, permissions (AppRelease).
- The `packages` object is an internal app→version index we can ignore.
- `index.xml` (F-Droid **v1 client** format) has the same data flattened into
  `<application>` / `<package>` elements; serve it unchanged, parse
  `index-v1.json` for the API.

### 2.2 APK placement & discovery (`update.py`)

- APK canonical file name is `{packageName}_{versionCode}.apk` inside the output
  dir `repo/` (produced by `fdroid update --rename-apks`, see §2.5).
- `get_apps_with_packages(apps, apks)` intersects `apps` (read from
  `metadata/*.yml`) with the scanned `repo/*.apk` files. So a listing = **have a
  metadata file AND have a matching APK**, then run `fdroid update`. APKs
  without metadata are dropped with `"has no metadata!"`.
- **`fdroid update` renames APKs itself** when run with `--rename-apks` (see §2.5)
  — the manager does not need to copy the upload to the canonical name.
- **`fdroid update --create-metadata` writes a *skeleton* yml** for an APK that
  has none (`Name` from the APK label; everything else empty) — a fallback, not
  a replacement for the manager's rich-metadata writer.

### 2.3 Per-release changelog / "what's new"

- fdroidserver reads per-version changelog text from
  `metadata/<packageName>/<locale>/changelogs/{versionCode}.txt` (plus
  `default.txt` as a fallback) — `update.py:insert_localized_app_metadata`.
- **Verified caveat:** `_set_localized_text_entry(..., versionCode=…)` writes
  `whatsNew` only into `app["Builds"]` entries — i.e. **source-build repos**.
  For a **binary-only** repo (no `Builds:` in the yml), fdroid does not attach a
  per-version `whatsNew` to the released APK in `index-v1.json`.

  ⇒ Decision: write the changelog into the fdroid-native path anyway
  (`metadata/{pkg}/en-US/changelogs/{versionCode}.txt`) so the data lives next
  to the metadata (no DB copy) and is picked up automatically if a `Builds`
  entry is ever added; the manager's UI reads **that same sidecar** for
  display. Re-verify the binary-repo wiring at implementation time; the
  sidecar is the fallback reader either way.

### 2.4 Signing keys stay manager-owned

`metadata/*.yml` only records **fingerprints** (`AllowedAPKSigningKeys`); the
private key material is *not* part of fdroid's files. The manager must keep the
keystores + `AppKey` rows (encrypted store passwords) to sign unsigned uploads
and to verify pre-signed uploads. So `AppKey` (and `KeyPath`) remain in the DB.

### 2.5 What `fdroid update` does and doesn't (verified in a sandbox)

Ran `fdroid init` then `fdroid update` against a throwaway repo with a mis-named
APK (`repo/upload_tmp.apk`) and no metadata, using the *test-only* fdroidserver
2.4.5 + SDK at `/srv/fdroid-mgr/android-sdk` (deliberately **not** used for
anything the product depends on):

| invocation | observed |
|---|---|
| plain `fdroid update` | warns `upload_tmp.apk (org.example.helloworld) has no metadata!` and **drops it from the index**; file name left unchanged; generates + signs the index artifacts |
| `--rename-apks` | **renames** the APK to `org.example.helloworld_2.apk` (also implies `--clean`) |
| `--create-metadata` | **creates `metadata/org.example.helloworld.yml`** skeleton — `Name: Hello World` (from APK label), `Summary`/`Description`/`License`/… empty |
| (any run) | **signs the index** (`index.jar`/`index-v1.jar`) with the repo key |
| (any run) | **does not touch the APK bytes** — SHA-256 identical before/after; it only verifies the signature and records `signer` (64-hex) + `sig` |

Consequences:

- **Delegate to `fdroid update`:** APK renaming (`--rename-apks`), index
  generation + index signing (already delegated), skeleton-metadata fallback
  (`--create-metadata`).
- **Keep in the manager (fdroid cannot do these):** signing *unsigned* uploads
  with the app key, and writing the *rich* metadata fields
  (`Summary`/`Description`/`License`/`WebSite`/`SourceCode`/`IssueTracker`/
  `AllowedAPKSigningKeys`) that the skeleton cannot populate. Per-version
  changelog is not accepted by `fdroid update` at all → the sidecar (§2.3)
  stays.

## 3. Design

### 3.1 New/changed services

**`FdroidRepoService`** (new) — read-only view over fdroid's files:

```csharp
public class FdroidRepoService
{
    // parse repo/index-v1.json into read models, or null when not yet generated
    public Task<FdroidIndex?> ReadIndexAsync(RepoConfig cfg, CancellationToken ct);

    // per-version changelog sidecar
    public static string ChangelogPath(string repoRoot, string packageName, int versionCode);
    public Task<string?> ReadChangelogAsync(RepoConfig cfg, string packageName, int versionCode, CancellationToken ct);
}

public record FdroidApp(string PackageName, string Name, string Summary, string Description,
    string License, string? Web, string? Source, string? Tracker,
    IReadOnlyList<FdroidVersion> Versions);

public record FdroidVersion(int VersionCode, string VersionName, string ApkName,
    string Sha256, long SizeBytes, string? SignerSha256, int? MinSdk, int? TargetSdk,
    string[] Permissions);
```

**`ReleaseService`** (refactor `PublishAsync`) — the only writer. Keep the
existing signature verification + monotonic versionCode checks + signing logic
(unchanged behavior), but change the side effects:

```csharp
// after signing/validating:
// 1. drop the apk into {RepoPath}/ under its upload name — NO canonical-name copy
//    (fdroid update --rename-apks performs the rename, §2.5)
// 2. write changelog → metadata/{pkg}/en-US/changelogs/{versionCode}.txt  (when provided)
// 3. _metadata.WriteAsync(app)                              (rich fields fdroid's skeleton can't fill)
// 4. await _index.GenerateStrictAsync(cfg, ct)               (fdroid update --rename-apks → new index-v1.json)
// 5. return the version read back from ReadIndexAsync(...)
// NO AppRelease row is created.
```

`RepoIndexService.GenerateAsync/GenerateStrictAsync` must pass `--rename-apks`
(always) so the canonical `{pkg}_{versionCode}.apk` name is fdroid's job, and
may pass `--create-metadata` as a last-resort skeleton fallback. Both variants
throw on `fdroid update` failure (strict already does) → the upload endpoint
returns 502.

### 3.2 The DB shrinks

| Table | Keep? | Why |
|---|---|---|
| `RepoConfig` | keep | repo identity/paths/secrets |
| `AppKey` | keep (+ add `PackageName`) | signing keys can't be re-derived from fdroid files |
| `AppInfo` | **drop** | replaced by `metadata/*.yml` + index-v1.json |
| `AppRelease` | **drop** | replaced by `repo/*.apk` + index-v1.json |

Apps/releases are keyed by **`packageName`** (`AppKey.PackageName`), not by a
numeric `AppId`. fdroid guarantees package-name uniqueness (it is the metadata
file stem).

### 3.3 Controllers (identity changes from `{id:int}` to `{packageName}`)

| Endpoint | Behavior |
|---|---|
| `GET /api/apps` | `FdroidRepoService.ReadIndexAsync` → map `apps` to cards |
| `GET /api/apps/{packageName}` | one entry from the index (+ keys/list from DB keyed by package) |
| `POST /api/apps` | write `metadata/{pkg}.yml` (+ generate key if asked) — from app-metadata work |
| `PUT /api/apps/{packageName}` | edit the yml fields, re-index |
| `DELETE /api/apps/{packageName}` | remove yml + `repo/{pkg}_*.apk` + changelogs, re-index |
| `GET /api/apps/{packageName}/releases` | `versions` from index-v1.json + changelog sidecar |
| `POST /api/apps/{packageName}/releases` | multipart upload (see §4) |
| `DELETE /api/apps/{packageName}/releases/{versionCode}` | remove `{pkg}_{vc}.apk` + changelog, re-index |
| `GET/POST /api/apps/{packageName}/keys` | existing key logic, re-keyed |

`AppsController`, `ReleasesController`, `KeysController` all switch the route
token. `GET /api/apps/{packageName}` returns
`{ packageName, name, summary, description, license, web, source, tracker, versions }`
directly from the index — one read, no DB join.

### 3.4 Upload flow (the "forward to fdroid" part)

`POST /api/apps/{packageName}/releases` (multipart: `apk`, optional `changelog`):

1. Resolve the app's signing key by package name (`KeyService`).
2. Parse the APK (`ApkService.ReadAsync`) → package must equal `{packageName}`;
   `versionCode` must be `> lastVersionCode` from the current index.
3. If unsigned → sign with the app's key. If signed → fingerprint must match the
   app's key (and, when the yml lists `AllowedAPKSigningKeys`, match that list).
4. Drop the APK into `{RepoPath}/` under its upload name — no manual canonical
   rename (that is `fdroid update --rename-apks`'s job).
5. Write the changelog sidecar (when provided).
6. Ensure `metadata/{packageName}.yml` exists/updated (`FdroidMetadataService`)
   — the rich fields only the manager knows, not fdroid's skeleton.
7. `fdroid update --rename-apks` (strict) → renames the APK, regenerates +
   signs `index-v1.json`, `index.xml`, …
8. Respond with the version read back from the fresh index (single source of
   truth — the API returns exactly what fdroid recorded).

### 3.5 De-duplication map — remove what `fdroid update` already does

Explicit removal of duplicated functionality, mapped to the code that must
change. **remove** = delete/stop doing it (fdroid owns it); **keep** = the
manager is the only place that can do it.

| Existing code | Does today | fdroid already does / can't do | Action |
|---|---|---|---|
| `ReleaseService.PublishAsync` — `File.Copy(tempPath, {RepoPath}/{pkg}_{vc}.apk)` | renames/copies the upload to the canonical name | `fdroid update --rename-apks` renames it | **remove** the canonical-name copy; drop the file under its upload name |
| `AppInfo` / `AppRelease` tables + read/write sites (`AppsController`, `ReleasesController`, `ReleaseService`, `RepoIndexService.GenerateAsync` count, `RepoController.Status`, `KeysController`, `KeyService` taking `AppInfo`) | parallel DB copy of app + release metadata | `metadata/*.yml` + `repo/index-v1.json` + `repo/*.apk` | **remove** the tables (after §6 migration); read fdroid's files |
| `RepoIndexService.GenerateAsync` | shells `fdroid update` (index gen + index signing) | — (correctly delegated today) | **keep**; just add `--rename-apks` (+optional `--create-metadata`) |
| `KeyService.SignApkAsync` | signs unsigned uploads with the app key | fdroid **never** signs app APKs (only verifies + records `signer`, §2.5) | **keep** (not duplicated) |
| `FdroidMetadataService.WriteAsync/Render` | writes the full yml (Name/Summary/Description/License/Web/… + `AllowedAPKSigningKeys`) | `--create-metadata` writes only a Name-filled skeleton | **keep** for rich fields; use `--create-metadata` only as a last-resort skeleton fallback |
| `ApkService.ReadAsync` (aapt badging) | reads package/versionCode/versionName/SDK/permissions before placing the APK | fdroid `scan_apk` is internal (no output the manager can reuse) | **keep** — thin pre-check needed to sign + validate *before* `fdroid update` |
| `ReleaseService` versionCode monotonic/duplicate check via `app.Releases` | enforces strictly-increasing versionCode | fdroid does **not** enforce this | **keep the rule**, but read `lastVersionCode` from index-v1.json instead of the DB |

Net effect: the manager keeps only signing (app keys), rich metadata authoring,
the versionCode business rule, and running `fdroid update`; every other
conversion (renaming, indexing, index signing, skeleton fallback) is fdroid's.

## 4. API contract

```
POST /api/apps/{packageName}/releases        (Authorize, multipart)
GET  /api/apps/{packageName}/releases        (Authorize)
DELETE /api/apps/{packageName}/releases/{versionCode}  (Authorize)
```

| Code | Body |
|---|---|
| `200` | `{ packageName, versionCode, versionName, apkFileName, sha256, sizeBytes, signerSha256, minSdk, targetSdk, permissions, changelog }` |
| `400` | `{ error }` — wrong package, versionCode not increasing, signer mismatch, bad APK |
| `404` | `{ error: "app not found" }` (no metadata yml) / `{ error: "release not found" }` |
| `409` | `{ error: "versionCode N already published" }` |
| `502` | `{ error: "fdroid update failed: …" }` (via `GenerateStrictAsync`) |
| `401` | unauthenticated |

`GET` returns an array of the per-version objects (newest first), each shaped
exactly like the `200` upload response. No DB round-trip — it is `index-v1.json`
`versions`, joined with the changelog sidecar.

## 6. Migration (one-time, in `Program.cs` startup)

On boot, before serving:

1. For every existing `AppInfo` row, ensure `metadata/{pkg}.yml` exists
   (`FdroidMetadataService.WriteAsync`) — app-metadata work already provides
   per-app writing; add a `MigrateAppsToMetadataAsync` sweep.
2. Backfill `AppKey.PackageName` from `AppId`.
3. Copy any recorded `AppRelease.Changelog` into
   `metadata/{pkg}/en-US/changelogs/{versionCode}.txt` (best-effort — the APKs
   are already in `repo/`).
4. Run `fdroid update` once → `index-v1.json` now fully describes apps+releases.
5. Drop (or stop using) `AppInfo` / `AppRelease`.

The result: publishing, listing and deleting all work the same as before, but
the data comes from fdroid's files, with the DB reduced to config + keys.

## 8. Security / operational notes

- `RepoPath` stays world-readable (F-Droid mirror requirement); metadata files
  are non-secret.
- Signing-key **private** material never leaves the manager (`KeyPath` +
  encrypted store passwords in `AppKey`); only fingerprints appear in the yml.
- The index is regenerated by the manager but treated as read-only input for
  the API (never hand-edited).
- `fdroid update` is the only writer of `index-v1.json`/`index.xml`.

### Implementation note (index-v1.json shape — corrects §2.1)

The §2.1 sample was copied from a stale `data/repo/index-v1.json` generated by
fdroidserver ≤1.x. The container-managed fdroidserver **2.x** (verified against
`/srv/fdroid/repo/repo/index-v1.json` and `fdroidserver/index.py:make_v1`)
writes a different v1 shape, which `FdroidRepoService.Parse` targets:

- `apps` is an **array** of `{ packageName, name, summary, description, license,
  webSite, sourceCode, issueTracker, categories, suggestedVersionCode, … }`
  (camelCase `webSite`/`sourceCode`/`issueTracker`, not `web`/`source`/`tracker`).
- `packages` is keyed by **packageName** → an **array** of `{ versionCode,
  versionName, apkName, hash, hashType, size, minSdkVersion, targetSdkVersion,
  signer, uses-permission }` (single `signer` hex, not `manifest.signer.sha256[]`).
- `repo.timestamp` / `added` / `lastUpdated` are **milliseconds**.
- The `packages` object's old `{AppId, VersionCode}` internal index from §2.1 is gone.

The parser also tolerates the legacy dict-keyed `apps` shape for robustness.

### Next-version suggestion (auto-increment from the previous release) — COMPLETED

`fdroid update` always reads `versionName`/`versionCode` from the **APK
manifest**; the manager cannot rewrite them without re-packaging the APK. So the
version is normally "pure user input" — whatever was baked into the APK at build
time. There is no `versionName` upload field: fdroid reads the manifest and any
form override would be ignored.

To get the same behaviour as the gatecontrol
`~/git/gatecontrol/mobileapp/increment_build_version.py` build-time helper (which
reads the previous release's version from the index and bumps patch + build
number), the manager now exposes that computation as an API:

```
GET /api/apps/{packageName}/releases/next-version   (Authorize, read scope)
```

```json
{
  "packageName": "org.example.app",
  "previousVersionName": "1.0.3",
  "previousVersionCode": 42,
  "versionName": "1.0.4",
  "versionCode": 43
}
```

- `versionName` — previous patch incremented ("1.0.3" → "1.0.4"; "1.0" → "1.0.1";
  a trailing `+build` is dropped since build number is `versionCode`).
- `versionCode` — previous highest + 1.
- No previous release → `"1.0.0"` / `1`; unknown app → `404`.

A CI pipeline hits this before building (replacing the python script): stamp the
returned `versionName`/`versionCode` into the Android manifest (Flutter:
`version: {versionName}+{versionCode}` in `pubspec.yaml`), then build and upload
as usual. The upload endpoint's monotonic `versionCode` check then sees the APK
carry exactly the suggested next code. The Web UI also pre-fills the version
field with this suggestion.
